## ✅ Resolved — commit sizing gate shipped (advisory soft cap + hard cap)

### Shipped (this round)
`scripts/ci/check_commit_sizing.py` wired into `ci.yml` → `tooling-quality` job:
- **Soft cap** (default **2000 changed lines**): `::warning` — advisory, one-mission discipline reminder. Mirrors the exact Wave-4 pathology this issue cites (9 missions, +17,346 lines in `2a39b5e9`).
- **Hard cap** (default **10000 changed lines**): **build failure** with a split-the-commit directive — the reviewability/bisectability floor. A 17k-line commit can no longer land silently.
- Tunable without code changes via repo variables `COMMIT_SIZE_SOFT_LIMIT` / `COMMIT_SIZE_HARD_LIMIT` (owner may tighten to taste; defaults chosen to catch mega-commits while not blocking legitimate bulk-but-single-purpose changes like lockfiles — which the counter measures honestly via numstat).
- Works on push events (evaluates every non-merge commit in the push) and locally (`--range BASE..HEAD`).
- Verified locally: 5 recent commits → `0 over hard cap, 0 over soft cap`; lint+format clean.

Note on policy scope: the repo's own history (bot evidence regens, vendored files) means defaults are conservative; the point of #475's "Smallest-First Increments" is enforced as a hard cap against mega-commits and as continuous advisory pressure below that.
