## 📊 #468 Latency Analysis — measured budget, root causes, and concrete follow-ups (Round 19)

### 1. What we measured today (2026-09-19, main @ b387e39+, external probes ×5 each)

| probe | endpoint | observed (external, sandbox→US-east) |
|---|---|---|
| Primary | `/` | 157–238 ms |
| Primary | `/api/v1/health` (deep) | 122–299 ms |
| Primary | `/health` (monitor's probe) | 142–269 ms |
| Worker | `/health` (same probe, same RTT) | 65–153 ms |
| Primary DB check (in-body `latency_ms`) | `SELECT 1` via pool | **18–145 ms** (variable) |

**Primary − Worker delta ≈ 60–120 ms per probe.** The monitor probes `/health` on all four nodes; on primary that endpoint runs the deep check (DB `SELECT 1` + pool checkout + memory check) — sibling nodes return without DB work.

### 2. Latency budget decomposition (Primary, per deep-health probe)

1. **Network physics**: ~150–200 ms RTT from South-Asia monitors to US-east (unfixable by code; the issue itself notes the ~250 ms physical floor for the overall average).
2. **Deep-health DB check**: `SELECT 1` incl. pool checkout — the platform's own `core/health_routes.py` comment already documents **~100–180 ms** cost; today's live samples ranged 18–145 ms. A 10 s response cache exists (`cache_hit` alternates with the probe cadence — misses pay the full check).
3. **Cross-region Redis mismatch (real-user API calls, not probes)**: the Upstash 5-node federation (`#460`) lives in **ap-southeast-1** while Render nodes are US-east → every rate-limiter/idempotency Redis round-trip costs ~**200+ ms** of app-side latency on non-health API calls.
4. **Middleware stack**: 15 middlewares; auth = local JWT (no per-request Redis), rate limiter skips health paths — CPU-only, negligible vs. (1)–(3).

### 3. Concrete follow-ups (ordered by expected impact)

| # | action | owner? | expected effect |
|---|---|---|---|
| 1 | Provision a **US-east Upstash node for the rate limiter** (keep ap-southeast federation for other uses) — `RATE_LIMIT` Redis URL split | **Owner** (dashboard) | −150–250 ms on every rate-limited API call |
| 2 | Bump deep-health cache TTL 10 s → 15 s (matches probe cadence → every probe served from cache; DB outage visibility delayed ≤15 s, still within Render health-check policy) | Bot (code, low risk) | −20–145 ms per probe on primary |
| 3 | Pre-warm the SQLAlchemy pool at boot (parallel pool checkout) so the first probe after deploy doesn't pay cold-pool cost | Bot (code) | removes deploy-window latency spikes |
| 4 | Edge-cache `/` and static SPA assets via Firebase Hosting CDN (already CDN-served) — verify `Cache-Control` on primary `/` JSON (currently uncachable) | Bot (code, cosmetic) | n/a for probes |

### 4. Status of the <100 ms target
<100 ms **edge-cached** is achievable for SPA/static paths (CDN), and for API responses whose *app-side* budget we can drive to <30 ms (items 1–3 remove the dominant app-side costs). The transatlantic RTT floor (~150–250 ms) for uncached dynamic calls from South Asia is physics — the correct lever there is CDN/edge presence, which the Firebase-hosted SPA already provides for the user-visible surface.
