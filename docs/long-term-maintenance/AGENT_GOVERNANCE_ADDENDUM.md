## কেন এই addendum

লক্ষ্য: **কম human effort + AI-এর সর্বোচ্চ বুদ্ধিমত্তা ব্যবহার — দুটোই একসাথে**, কিন্তু নিয়ন্ত্রণ ছাড়া নয়।

`.agents/AGENTS.md`-এ "১০০% autonomy, থামবে না" দর্শন আছে। এটা ভুল না — কিন্তু এই দর্শনের একটা observed side-effect হলো: একাধিক agent concurrently কাজ করলে (memory অনুযায়ী already ঘটেছে) প্রতিটা agent independently "সেরা" সিদ্ধান্ত নেয়, যেটা একসাথে conflict তৈরি করে (class rename, নতুন test suite, code-vs-test mismatch)। সমাধান autonomy কমানো না — **coordination ও verification layer যোগ করা**, যাতে human-কে conflict resolve করতে বসতে না হয়।

এই addendum তিনটা নতুন layer প্রস্তাব করে। প্রতিটাই bounded — agent-এর সিদ্ধান্ত নেওয়ার স্বাধীনতা কমায় না, শুধু "একই সময়ে দুইজন একই জিনিস না ভাঙুক" নিশ্চিত করে।

## ১. Work-Claim Ledger (concurrent-agent conflict এড়াতে)

**সমস্যা:** দুইটা session/agent একই module-এ একসাথে কাজ করলে কেউই জানে না অন্যজন কী করছে।

**প্রস্তাব:** কাজ শুরুর আগে agent একটা লাইন লিখবে `docs/audit_reports/ACTIVE_CLAIMS.md`-এ (ফাইলটা না থাকলে বানাবে):

```
| Session ID | Module/ফাইল | শুরু সময় (UTC) | কাজের ধরন |
|---|---|---|---|
| <auto-generated> | backend/core/orchestrator.py | 2026-08-06T10:00Z | rename class X→Y |
```

কাজ শুরুর আগে এই টেবিল পড়ে দেখবে ঐ module-এ অন্য কোনো active claim আছে কিনা। থাকলে — সেই module স্কিপ করে ভিন্ন module ধরবে, বা user-কে জানাবে conflict সম্ভাবনা আছে। কাজ শেষে নিজের row মুছে দেবে বা "done" মার্ক করবে।

এটা lightweight — কোনো external locking service লাগে না, শুধু একটা markdown convention।

## ২. Pre-Commit Sanity Gate (broken commit ঠেকাতে)

**সমস্যা:** CQ-001 (syntax error) কমিট হয়ে গিয়েছিল, CI ধরার আগেই — কারণ কোনো agent commit-এর আগে নিজে verify করেনি।

**প্রস্তাব:** যেকোনো `.py`/`.ts`/`.tsx` ফাইল edit করার পর, `git commit`-এর ঠিক আগে agent বাধ্যতামূলকভাবে চালাবে:

```bash
# Python ফাইল বদলালে
python3 -m py_compile <changed_file>

# TS/TSX ফাইল বদলালে
npx tsc --noEmit <changed_file>   # বা প্রজেক্টের tsconfig অনুযায়ী

# উভয় ক্ষেত্রে
ruff check <changed_file>
```

এটাই [`CODE_QUALITY_CHECK_SEQUENCE.md`](./CODE_QUALITY_CHECK_SEQUENCE.md)-এর **Layer 1 ও 2**, শুধু commit-এর আগে locally, CI wait না করে। এই দুটো layer দ্রুত (single-file, no execution) — তাই human effort বা agent speed-এ কার্যত কোনো cost নেই, কিন্তু broken commit স্থায়ীভাবে ঠেকিয়ে দেয়।

**নিয়ম:** এই gate fail করলে commit করা যাবে না — নিজে ফিক্স করে আবার চেষ্টা করবে (AGENTS.md-এর existing "২বার fail করলে থামো" rule অনুযায়ী, ২বারের বেশি loop করবে না)।

## ৩. Blast-Radius Classification (risk অনুযায়ী autonomy)

**সমস্যা:** একটা variable rename আর একটা auth/payment/schema পরিবর্তন — বর্তমানে একই মাত্রায় "থামবে না" প্রযোজ্য।

**প্রস্তাব:** কাজ শুরুর আগে agent নিজের কাজকে classify করবে:

| Tier | উদাহরণ | Autonomy |
|---|---|---|
| **LOW** | variable/function rename, comment, dead code removal, lint fix | পুরোপুরি autonomous, approval লাগবে না |
| **MEDIUM** | নতুন ফাংশন/মডিউল যোগ, existing logic পরিবর্তন যা অন্য মডিউলকে touch করে না | Autonomous, কিন্তু commit message-এ "MEDIUM-RISK" ট্যাগ + PHASE_LOG-এ এন্ট্রি বাধ্যতামূলক |
| **HIGH** | auth/permission logic, payment (Stripe/SSLCommerz), DB schema migration, secret/env handling, production deploy config (`supreme-core-ci.yml`-এর deploy job গুলো), CI gate condition (যেমন repo-check) | **Explicit user confirmation লাগবে** — AGENTS.md-এর "১০০% autonomy" এখানে প্রযোজ্য না |

এটা AGENTS.md-এর existing rule ("Conflict Resolution & Admin Permission Rule") থেকেই এক্সটেনশন — সেটা শুধু conflict-এর সময় admin permission চায়, এটা **HIGH-tier কাজের জন্য preemptively** চায়, conflict হওয়ার আগেই।

**উদাহরণ যা আমরা এই session-এই পেয়েছি:** `service_preflight_check.py`-এর deploy-credential logic পরিবর্তন করা HIGH-tier — তাই এটা এখনো apply করিনি, শুধু ready রেখেছি আপনার approval-এর জন্য। এটাই এই tier-এর সঠিক আচরণের উদাহরণ।

## ৪. Technical Enforcement — CODEOWNERS (এটাই আসল "দাঁত")

**সমস্যা:** উপরের ৩টা layer সবই markdown/policy-based — agent নিজে মানবে এই ভরসায় নির্ভর করে। AGENTS.md-এ আগে থেকেই "production-ready, no mock" লেখা থাকা সত্ত্বেও payment integration mock অবস্থায় ছিল — অর্থাৎ শুধু policy লিখে রাখলেই guarantee হয় না।

**⚠️ Correction (2026-08-06):** প্রথম সংস্করণে এই gate ভুলবশত এই (staging) repo-তে বসানো হয়েছিল। কিন্তু dual-repo architecture অনুযায়ী **staging repo হলো AI-এর free work zone** — payment/auth/যেকোনো কোড এখানে বাধাহীনভাবে push/pull/correct/improve হবে, কারণ এখান থেকে কখনো production deploy হয় না। **আসল gate থাকা উচিত `paykaribazaronline/supremeai` (main/production repo)-তে।**

**এই repo (staging)-এ শুধু governance self-protection:**

`.github/CODEOWNERS` (এই repo-তে) শুধু `.agents/**`, `AGENTS.md`, `.github/CODEOWNERS` protect করে — যাতে কোনো agent নিজের safety rule নিজেই চুপচাপ মুছে দিতে না পারে। বাকি সব (payment, auth, config, ইত্যাদি) সম্পূর্ণ free।

**Production repo (`paykaribazaronline/supremeai`)-এ পূর্ণ CODEOWNERS:** payment/billing, auth, secrets/env, DB migration, deploy config (`.github/workflows/**`), `.agents/**` — সব admin-এর mandatory review-এর আওতায়। এই ফাইলটা ঐ repo-তে আলাদাভাবে যোগ করতে হবে (এই staging repo-র token দিয়ে সেখানে push করা যায় না — আলাদা scoped token লাগবে, অথবা admin নিজে GitHub UI থেকে যোগ করতে পারেন)।

`paykaribazaronline/supremeai`-তে "Require a pull request before merging" বিশেষভাবে গুরুত্বপূর্ণ — এটাই সেই gap বন্ধ করে দেয় যেখানে `main`-এ direct push করলেও deploy job trigger হয়ে যেত, staging→PR→admin-review flow সম্পূর্ণ বাইপাস করে (এই সমস্যাটা এই session-এর একদম শুরুতে ধরা পড়েছিল)।

## ৫. Freeze Switch (emergency one-click pause)

**সমস্যা:** কিছু ভুল হচ্ছে বুঝলে admin-কে token revoke করতে হয় বা workflow disable করতে হয় — কয়েক ধাপ, দেরি হয়।

**প্রস্তাব:** repo root-এ `.agents/FREEZE` নামে একটা ফাইল থাকলে (content যাই হোক), agent বাধ্যতামূলকভাবে **কোনো commit/push করবে না** — শুধু analysis/report করবে। ফাইলটা GitHub UI থেকে সরাসরি create/delete করা যায় (১০ সেকেন্ড, কোনো token লাগে না)।

## ৬. Checkpoint Tag (রোলব্যাক সেফটি নেট)

**সমস্যা:** MEDIUM/HIGH-tier কাজ apply করার পর কিছু ভাঙলে "আগের অবস্থায় ফিরে যাওয়া" ম্যানুয়ালি খুঁজে বের করতে হয়।

**প্রস্তাব:** MEDIUM বা HIGH-tier কাজ apply করার ঠিক আগে agent একটা lightweight tag বানাবে:

```bash
git tag checkpoint-$(date -u +%Y%m%d-%H%M) && git push origin --tags
```

কিছু ভুল হলে admin এক কমান্ডেই ফিরে যেতে পারবেন:

```bash
git reset --hard checkpoint-<timestamp> && git push --force-with-lease
```

**প্রস্তাব:** HIGH-tier প্রস্তাবিত পরিবর্তন কোডে না বসিয়ে `docs/audit_reports/PENDING_APPROVALS.md`-এ এক-লাইনে লিস্ট হবে। Admin-এর কাজ শুধু Decision কলামে `APPROVED`/`REJECTED` লেখা — পুরো diff/কোড ঘাঁটতে হবে না, চাইলে দেখতে পারেন লিংক থেকে।
