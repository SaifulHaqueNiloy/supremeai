# SupremeAI — Living Prompt Architecture & Protocol-Driven Simplification Plan
## "How 4–5 Living Prompts Replace 800+ Lines of Race-Condition & Distributed Locking Machinery"

> **তারিখ:** 2026-09-28  
> **স্ট্যাটাস:** Local Architectural Plan (Do Not Push)  
> **উদ্দেশ্য:** জটিল কোড ও ডিস্ট্রিবিউটেড লকিং মেশিনারির বদলে ৪–৫টি শক্তিশালী প্রম্পট-কন্ট্রাক্ট (Living Prompts) দিয়ে সিস্টেমকে হালকা, রেস-কন্ডিশন মুক্ত ও বুলেটপ্রুফ করা।

## ১. মূল দর্শন (The Core Philosophy)

> ### **“Code is a liability; Clear Protocol is leverage.”**
> **“যে সমস্যা সমাধান করতে মানুষ ৭০০–৮০০ লাইনের জটিল কোড লেখে, তার বেশিরভাগই কোডের সমস্যা নয়; সেটা ছিল Orchestration ও Protocol-এর অভাব।”**

সুপ্রিমএআই-এর অতীতে যখনই মাল্টি-এজেন্ট রেসিং, ফাইল কনফ্লিক্ট বা মেমোরি ইনকনসিস্টেন্সি দেখা দিয়েছে, ডেভেলপাররা কোড লিখে সমাধান করার চেষ্টা করেছে:
* ডিস্ট্রিবিউটেড মিউটেক্স ও লকিং মেকানিজম
* স্টেট সিঙ্ক্রোনাইজার ও জটিল ব্যাকঅফ লুপ
* হাজার লাইনের মনোলিথ প্যাচ ফাইল (`zero_cost_patch_phase1_4.py`, `config_classification.py`)

**বাস্তবতা:** কোড বাড়লে বাগ বাড়ে, ডিপেন্ডেন্সি জটিল হয় এবং সিস্টেম স্ফীত হয়। কিন্তু যদি এজেন্টের কাজের সীমানায় **৪–৫টি সুনির্দিষ্ট Living Prompt Protocol** বসিয়ে দেওয়া যায়, তবে এই পুরো ৮০০+ লাইনের মেশিনারির কোনো প্রয়োজনই থাকে না।

## ২. সেই ৪–৫টি Living Prompt Protocol (যা ৮০০+ লাইন কোড বাঁচায়)

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   THE 5 LIVING PROMPT PROTOCOLS                        │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Slot Isolation:    1 Agent = 1 Dedicated Slot (coder-N)             │
│ 2. Atomic Claim Lock: 1 Issue = 1 Claim + Touching Files Declaration   │
│ 3. Atomic Blast:      1 Issue = 1 Branch = 1 PR (Max 1-2 files)        │
│ 4. Verify First:      No Verification, No Code, No Delete              │
│ 5. Safe Gate:         Open PR with `queue:hold` (Human Signs Off)      │
└────────────────────────────────────────────────────────────────────────┘
```

### প্রোটোকল ১: Slot Isolation (`acquire_role_slot.py`)
* **যা বাঁচায়:** কোনো সেন্ট্রাল প্রসেস সুপারভাইজার বা থ্রেড ম্যানেজমেন্ট কোডের দরকার নেই।
* **নিয়ম:** প্রতিটি এজেন্ট আলাদা স্লট ব্রাঞ্চে কাজ করবে (`coder-1`, `coder-2`, ...)। এক এজেন্ট কখনো অন্যের ব্রাঞ্চ স্পর্শ করবে না।

### প্রোটোকল ২: Atomic Claim Lock & File Declaration
* **যা বাঁচায়:** ~৪০০ লাইনের ডিস্ট্রিবিউটেড ফাইল লকার, রেস কন্ডিশন রিজলভার ও ডেডলক ডিটেক্টর।
* **নিয়ম:** কাজ শুরুর আগে গিটহাব ইস্যুতে ক্লেইম লক নেবে এবং কমেন্টে স্পষ্ট ঘোষণা দেবে:  
  `Touching files: path/to/file1.py, path/to/file2.py`  
  এতে অন্য কোনো এজেন্ট সেই ফাইলে হাত দেবে না। রেসিং গোড়া থেকেই অসম্ভব।

### প্রোটোকল ৩: Verify First (No Verification, No Code, No Delete)
* **যা বাঁচায়:** ~৩০০ লাইনের ফ্র্যাজাইল পোস্ট-হক লিন্টার, রানটাইম ক্র্যাশ হ্যান্ডলার ও রিভার্ট বটস।
* **নিয়ম:** স্ট্যাটিক অনুমানে কোনো ফাইল ডিলিট বা কোড এডিট নিষিদ্ধ। পরিবর্তনের আগে ও পরে ৩-স্তর যাচাই (Dynamic Reflection, Boot Smoke Test, Pytest) প্রত্যক্ষ প্রমাণ হিসেবে PR-এ দিতে হবে।

### প্রোটোকল ৪: Atomic Blast Radius (1 Issue = 1 Branch = 1 PR)
* **যা বাঁচায়:** মেগা মার্জ-কনফ্লিক্ট সলভার ও কমপ্লিকেটেড রিবেস আর্কিটেকচার।
* **নিয়ম:** একটি PR-এ সর্বোচ্চ ১–২টি ফাইল স্পর্শ করা যাবে। ছোট ও আইসোলেটেড পরিবর্তনের ফলে কনফ্লিক্ট ব্লাস্ট রেডিয়াস শূন্য হয়ে যায়।

### প্রোটোকল ৫: Safe Gate (`queue:hold`)
* **যা বাঁচায়:** স্বয়ংক্রিয় ভুল মার্জ সামলানোর শত শত লাইনের রোলব্যাক পাইপলাইন।
* **নিয়ম:** প্রতিটি PR স্বয়ংক্রিয়ভাবে `queue:hold` লেবেলে থেমে থাকবে। হিউম্যান রিভিউ করার পর সবুজ সংকেত দিলেই কেবল তা মেইনে মার্জ হবে।

## ৩. Living Prompt-এর আর্কিটেকচার (জীবন্ত রূপ)

স্ট্যাটিক প্রম্পট যেখানে অন্ধ, Living Prompt সেখানে রিয়েল-টাইম সিস্টেমের সাথে যুক্ত হয়ে নিজেকে প্রতিনিয়ত আপডেট করে:

```text
                     [ GITHUB & SYSTEM STATE ]
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     │                           │                           │
Active Phase Status      Collective Memory          Peer Claim Locks
(Phase 0 / 1 / 2)       (LESSONS_LEARNED.md)     (Touching files radar)
     │                           │                           │
     └───────────────────────────┼───────────────────────────┘
                                 ▼
                     [ LIVING PROMPT ENGINE ]
                     (scripts/agents/living_prompt.py)
                                 │
                                 ▼
                    🧬 Generated Agent Prompt
                    (Tailored, Safe & Immune)
```

### Living Prompt-এর ৪টি সুপারপাওয়ার:
1. **কালেক্টিভ ভ্যাকসিন (Collective Vaccine):** কোনো এজেন্ট কোনো লাইব্রেরি বা সিস্টেমে নতুন বাগ ফেস করে ফিক্স করলে, তা স্বয়ংক্রিয়ভাবে পরবর্তী এজেন্টের প্রম্পটে সতর্কতা হিসেবে ইনজেক্ট হবে। একই ভুল সিস্টেমে দুবার হবে না।
2. **অটো-ফেজ ট্রানজিশন:** Step 1-এর সব ইস্যু শেষ হলে প্রম্পট স্বয়ংক্রিয়ভাবে Step 2-এর মেগা কনসলিডেশনের নির্দেশ দেবে—মানুষকে কিছুই বলতে হবে না।
3. **রিয়েল-টাইম কনফ্লিক্ট রাডার:** অন্য কোনো এজেন্টের ক্লেইম করা ফাইলগুলো নতুন এজেন্টের প্রম্পটে "LOCKED" হিসেবে দেখানো হবে।
4. **দ্য ডুয়াল-স্টেট গেম (Solver ➔ Peer-Reviewer Dynamic Loop):**  
   এজেন্ট কখনো অলস বসে থাকবে না বা সময়ের আগে পরবর্তী ধাপে লাফ দেবে না। যতক্ষণ Step 1-এর কোনো আনক্লেইমড ইস্যু থাকবে, এজেন্ট সলভার হিসেবে কাজ করবে। সব ইস্যু ক্লেইম হয়ে গেলে বাকি এজেন্টরা স্বয়ংক্রিয়ভাবে **Peer Reviewer** মোডে চলে গিয়ে সহকর্মীদের PR অডিট করবে!

### ৩.১ দ্য ডুয়াল-স্টেট গেম আর্কিটেকচার (The Dual-State Agent Game)

> ### **“No Claim Left Behind; No PR Left Unreviewed.”**
> **“১টি এজেন্ট থাকলে সে একাই সব কাজ টেনে শেষ করবে। ৫–১০টি এজেন্ট থাকলে তারা কাজ দ্রুত ভাগ করে নেবে; আর কাজ শেষ হলে বাকিরা রিভিউয়ার হয়ে প্রতিটি PR-এ ইনডিপেনডেন্ট ফিডব্যাক দিয়ে হিউম্যান রিভিউকে পানির মতো সহজ করে তুলবে।”**

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        THE DUAL-STATE AGENT GAME LOOP                                  │
├────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                        │
│   [ START LOOP ] ──► Check: Any unclaimed Step 1 (P1-high) issue?                      │
│                            │                                                           │
│           ┌────────────────┴────────────────┐                                          │
│           ▼ YES                             ▼ NO (All claimed / closed)                │
│    ┌──────────────┐                  ┌──────────────────┐                              │
│    │ STATE A:     │                  │ STATE B:         │                              │
│    │ SOLVER MODE  │                  │ REVIEWER MODE    │                              │
│    └──────┬───────┘                  └────────┬─────────┘                              │
│           │                                   │                                        │
│           ▼                                   ▼                                        │
│    1. Atomic Claim Issue               1. Check open PRs with `queue:hold`             │
│    2. Branch in Dedicated Slot         2. Fetch PR diff & inspect changes              │
│    3. 3-Tier Verification (No Delete)  3. Run local reflection & smoke tests           │
│    4. Push PR with `queue:hold`        4. Post structured Peer Review comment          │
│           │                                   │                                        │
│           └────────────────┬──────────────────┘                                        │
│                            ▼                                                           │
│                   [ REPEAT NEXT CYCLE ]                                                │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### এই গেমের ৩টি মাস্টারক্লাস বেনিফিট ও কন্সটিটিউশনাল টপোলজি:
1. **৯ Coder Agent + ১ PR-Helper Agent টপোলজি:**
   - **৯টি Coder Agent (`coder-1` থেকে `coder-9`):** কাজ ফাঁকা থাকলে কোড লিখে PR দেবে (State A), কাজ শেষ হলে বাকিদের PR-এ নিরপেক্ষ রিফ্লেকশন ও Peer Review দেবে (State B)।
   - **১টি PR-Helper Agent (`pr-helper-1` — স্টেশন মাস্টার):** সে কোড লিখবে না; তার কাজ হলো ওপেন PR-গুলোতে সহকর্মী কোডার এজেন্টদের Peer Feedback একত্রিত করা, সব ফিডব্যাক গ্রিন ও কনসেনসাস ঠিক থাকলে PR-টিকে Merge Train Rollup (`queue:pending-rollup`)-এ অন্তর্ভুক্তির অনুমোদন দেওয়া।
2. **দ্য (N - 1) পিয়ার-রিভিউ ল (The N - 1 Peer-Review Law):** কোনো এজেন্ট নিজের তৈরি PR নিজে রিভিউ করতে পারবে না (Strictly Rule 12: No Self-Review)। তাই ৯ জন কোডার এজেন্ট একে অপরের PR-এ গভীর Peer Review দেবে, আর PR-Helper সেই ফিডব্যাক অডিট করে ট্রেনের অনুমোদন দেবে।
3. **দ্য রুল অফ থ্রি ও রিভিউ কোটা (The Rule of 3 Review Quota):**
   - ৯ বা ১০ জনের জন্য অপেক্ষা করে বসে থেকে সিস্টেমকে স্লো করা যাবে না। প্রতিটি PR ল্যান্ড করার জন্য **মিনিমাম ৩টি রিভিউ আবশ্যক** (ম্যাক্সিমাম যত বেশি এজেন্ট সক্রিয় থাকে, তত বেশি রিভিউ অনুমোদিত)।
   - **ম্যান্ডেটরি ৩টি রিভিউর উপাদান:**
     - **রিভিউ ১ (অল্টারনেটিভ কোডার):** কমপক্ষে ১টি রিভিউ অন্য কোডার এজেন্টের কাছ থেকে হতে হবে (Rule 12: No Self-Review)।
     - **রিভিউ ২ (PR-Helper):** কমপক্ষে ১টি রিভিউ PR-Helper এজেন্টের ট্রাফিক্স ও কনসেনসাস অডিট হতে হবে।
     - **রিভিউ ৩ (২য় পিয়ার কোডার অথবা ৩০-মিনিট ফলব্যাক):** দ্বিতীয় আরেকজন কোডার এজেন্টের রিভিউ। যদি ৩০ মিনিটের মধ্যে ২য় কোনো এজেন্ট ফ্রি না থাকে, তবে **SupremeAI Engine নিজে ৩০ মিনিট পর ৩য় রিভিউ সম্পন্ন করবে** (জিরো ডেডলক গ্যারান্টি)।
4. **রিভিউয়ের ৪টি সুনির্দিষ্ট মানদণ্ড (The 4-Pillar Review Rubric):**
   - (১) *Philosophy Compliance:* ঘুড়ি ও নাটাই নীতি মেনে চলা হয়েছে কি না?
   - (২) *True Benefit:* কোডবেসের পরিচ্ছন্নতা, সাইজ রিডাকশন বা কোয়ালিটিতে বাস্তব সুবিধা তৈরি হয়েছে কি না (কোনো ফেইক মক নয়)?
   - (৩) *Zero Regression (Rule 21):* কোনো টেস্ট ডিলিট বা স্কিপ করা হয়েছে কি না?
   - (৪) *Scope Narrowness:* দাবি করা ইস্যুর অতিরিক্ত কোনো ড্রাইভ-বাই রিফ্যাক্টরিং করা হয়েছে কি না?
5. **জিরো-টাচ কন্টিনিউয়াস অটোনমি (Zero-Touch Continuous Autonomy):** ৩টি ভেরিফায়েড রিভিউ এবং মার্জ ট্রেনের ফুল-স্যুট ইন্টিগ্রেশন গেট গ্রিন হলে মার্জ ট্রেন স্বয়ংক্রিয়ভাবে `main`-এ ল্যান্ড (`MERGE_TRAIN_AUTO_LAND`) করবে।
6. **অ্যাডমিন ওভাররাইট ও সার্বভৌম কর্তৃত্ব (Admin Overwrites Everything):**
   - অ্যাডমিন যেকোনো মুহূর্তে যেকোনো রিভিউ, গেট বা অটো-মার্জ ডিসিশন সম্পূর্ণ ওভাররাইট করার নিরঙ্কুশ ক্ষমতার অধিকারী।
   - সিস্টেম কেবল তখনই হিউম্যান অ্যাডমিনের সিদ্ধান্তের জন্য পজ করবে, যদি (ক) কোর ফিলোসফিতে আঘাত আসে, অথবা (খ) এমন কোনো ঘটনা ঘটে যার জন্য পূর্বে কোনো ইস্যু তৈরি করা ছিল না।
7. **অর্ডারড সিকোয়েন্সিয়াল মার্জ ট্রেন ও রিয়েল কনফ্লিক্ট ডিটেকশন (Ordered Sequential Rollup Train):**
   - কোনো উচ্চতর ক্রমের PR (যেমন: PR seq:2) কখনোই তার পূর্ববর্তী PR (PR seq:1) মার্জ হওয়ার আগে ট্রেনের বেসলাইনে ঢুকবে না।
   - PR seq:1 ট্রেনের বেসলাইনে ল্যান্ড করার পর, তার পরিবর্তনের ওপর PR seq:2-কে মার্জ করা হবে (`Train Base + PR-1` এর ওপর PR-2)।
   - এতে PR seq:2 যদি ভুলবশত PR seq:1-এর কোনো ডিলিট করা ফাইল ইম্পোর্ট করে বা সিনট্যাক্স সংঘাত তৈরি করে, তবে তা অবিলম্বে **রিয়েল কনফ্লিক্ট** হিসেবে ধরা পড়বে।
8. **ইস্যু তৈরির সময় বাধ্যতামূলক গ্রুপ ও সিকোয়েন্স মেটাডাটা (Mandatory Group & Sequence Metadata):**
   - এই সিকোয়েন্সিয়াল চেইন কাজ করার জন্য যেকোনো ফেজড কাজের ইস্যু তৈরির সময় অবশ্যই মেটাডাটা/লেবেলে গ্রুপ (`group:step-1`) এবং সিকোয়েন্স নম্বর (`seq:1`, `seq:2`, `seq:3`...) নির্ধারিত থাকতে হবে।
   - PR-Helper ট্রেন তৈরির সময় PR-গুলোকে তাদের `(group, seq)` অনুযায়ী আরোহী ক্রমে (Ascending Order) ট্রেনে ওঠাবে।
9. **কন্টিনিউয়াস ইনক্রিমেন্টাল রোলআপ ও ধারাবাহিক ক্রম মেলানোর নিয়ম (Contiguous Incremental Rollup Engine):**
   - ট্রেনের জন্য ১৪টি PR জমা হওয়ার কোনো অপেক্ষা নেই। যদি কেবল PR-1 প্রস্তুত হয়, ট্রেন PR-1 কে নিয়েই রওনা দেবে।
   - যদি PR-1, PR-2 এবং PR-4 প্রস্তুত হয় (মাঝের PR-3 তখনো আসেনি), তবে ট্রেন দীর্ঘতম ধারাবাহিক ক্রম `[PR-1, PR-2]` কে নিয়ে চলে যাবে। PR-4 স্টেশনে অপেক্ষা করবে যতক্ষণ না PR-3 এসে শিকল সম্পূর্ণ করে।

## ৬. বাস্তবায়ন ঝুঁকি অডিট ও ইকোসিস্টেম চোকহোল্ড শিল্ড (The 5 Risks & The Ecosystem Chokehold)

> ### **“You may be king, but বাপেরও বাপ আছে!”**
> **“আমাদের সিস্টেম একটি স্বয়ংসম্পূর্ণ ইকোসিস্টেম — মেথডোলজিতে এজেন্টকে কাজের পূর্ণ স্বাধীনতা (ঘুড়ি ওড়ানো) দেওয়া হলেও, পেরিমিটারে সিস্টেম এমনভাবে নাটাই ধরে রাখে যে বাউন্ডারি অতিক্রমের কোনো সুযোগ নেই।”**

৭০% কোড ডিলিট করে সিস্টেম ৩০%-এ নামিয়ে আনার ক্ষেত্রে ৫টি সুনির্দিষ্ট ঝুঁকি রয়েছে। নিচে সেই ঝুঁকি এবং তাদের মোকাবেলায় সিস্টেমের স্বয়ংক্রিয় গার্ডরেল (Chokeholds) তুলে ধরা হলো:

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        THE ECOSYSTEM CHOKEHOLE SHIELD ARCHITECTURE                     │
├────────────────────────────────────────────────────────────────────────────────────────┤
│  Agent Freedom (Inside)  ──► [ HOW: Write code, adapt, test freely ]                  │
│                                           │                                            │
│  SPOOLS & CHOKEPOINTS    ──► 1. Pre-push Hook: Blocks un-declared file touch           │
│  (The "বাপের বাপ" Gates)  ──► 2. PR Gate: Enforces 100% green tests & no test deletion │
│                          ──► 3. Queue Hold: No self-merge, human signs off             │
│                          ──► 4. Git Tag Archive: Historical memory permanently kept    │
│                          ──► 5. DB Migration Squash: Zero Alembic divergence           │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### ঝুঁকি ১: ডাইনামিক রিফ্লেকশন ও হিডেন ডিপেন্ডেন্সি ব্রেক হওয়া (Hidden Dependency Break)
* **ঝুঁকি:** ১.২৫ মিলিয়ন লাইনের সিস্টেমে কিছু ফাইল রানটাইমে স্ট্রিং বা রিফ্লেকশন দিয়ে কল হতে পারে (`importlib.import_module()`)। অন্ধভাবে ডিলিট করলে রানটাইমে ক্র্যাশ হতে পারে।
* **🛡️ ইকোসিস্টেম চোকহোল্ড (The Shield):**
  * **৬-দফা ভেরিফিকেশন ডিসিপ্লিন (Ground Truth Verification):**
    1. গ্লোবাল টেক্সট ও স্ট্রিং সার্চ (`grep -rn "target_module"`).
    2. বুট স্মোক টেস্ট (`python -c "import main"`).
    3. রিভার্স টেস্ট স্যুট এক্সিকিউশন।

### ঝুঁকি ২: প্রম্পট ড্রিফ্ট ও এলএলএম হ্যালুসিনেশন (Prompt Drift / Weak Models)
* **ঝুঁকি:** কোডের হার্ড রুল না থাকলে দুর্বল এলএলএম মডেল প্রম্পট ভুলে গিয়ে অনির্ধারিত ফাইলে হাত দিতে পারে বা রুলস বাইপাস করার চেষ্টা করতে পারে।
* **🛡️ ইকোসিস্টেম চোকহোল্ড (The Shield):**
  * প্রম্পটের ওপর অন্ধ বিশ্বাস নয়! সিস্টেম-লেভেল গিট হুক্স:
    * `scripts/git/pre-push` পুশ ব্লক করবে যদি `Touching files:` ঘোষণার বাইরে ফাইল মডিফাই হয়।
    * **`queue:hold` ইনভেরিয়েন্ট:** এজেন্ট নিজের PR কখনো নিজে মার্জ করতে পারবে না। হিউম্যান চোখ দিয়ে দেখার পরই কোড ঢুকবে।

### ঝুঁকি ৩: গিটহাব এপিআই রেট লিমিট ও থ্রটলিং (GitHub API Rate Limits)
* **ঝুঁকি:** মাল্টি-এজেন্ট যদি স্টেট মেশিনের জন্য প্রতি মিনিটে গিটহাব এপিআই-তে হিট করে, তবে গিটহাবের ৫,০০০ রিকোয়েস্ট/ঘণ্টার লিমিট শেষ হয়ে যেতে পারে।
* **🛡️ ইকোসিস্টেম চোকহোল্ড (The Shield):**
  * `next_claimable.sh`-এ লোকাল গিট ফেচ ক্যাশিং এবং এক্সপোনেনশিয়াল ব্যাকঅফ লুপ।
  * সেকেন্ডারি স্টেট মিরর হিসেবে লোকাল Redis ক্যাশ রাখা।

### ঝুঁকি ৪: `docs/` ডিলিট করার সময় ঐতিহাসিক বিজনেস নলেজ হারিয়ে যাওয়া
* **ঝুঁকি:** ২.৭৬ লাখ লাইনের ডকস ও পুরনো ফেজ প্ল্যান ডিলিট করলে অতীতের কোনো জটিল ডোমেন লজিক বা RAG নলেজ হারিয়ে যেতে পারে।
* **🛡️ ইকোসিস্টেম চোকহোল্ড (The Shield):**
  * **Permanent Git Tag Archive:** মুছে ফেলার ঠিক আগের মুহূর্তে রিপোজিটরিতে পার্মানেন্ট ট্যাগ দেওয়া হবে:  
    `git tag archive/v1.0-pre-simplification && git push origin --tags`  
    এর ফলে গিট ট্রিতে ১.২৫ মিলিয়ন লাইনের পুরো ইতিহাস চিরদিনের জন্য সংরক্ষিত থাকবে।
  * প্রয়োজনীয় আর্কিটেকচারাল সারসংক্ষেপ মুছে ফেলার আগেই Supabase pgvector মেমোরিতে এম্বেড করে ফেলা হবে।

### ঝুঁকি ৫: Alembic মাইগ্রেশন স্প্রল ও স্কিমা কনফ্লিক্ট (Migration Divergence)
